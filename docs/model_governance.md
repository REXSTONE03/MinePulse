# MinePulse AI — Model Governance Framework

This document outlines the model governance, version control, metadata tracking, and audit traceability framework for MinePulse AI, ensuring reproducibility and academic accountability.

---

## 1. Governance Concept & Architecture

Every parts-ordering recommendation or vehicle risk estimate generated by the system must be traceable back to the exact version of the model, feature definition, training dataset, and hyper-parameter configurations that produced it.

```
+-----------------------------------------------------------------------------------+
|                              model_governance (Registry)                          |
+-----------------------------------------------------------------------------------+
| - model_id (PK)                                                                   |
| - model_version (e.g. "v1.0.0")                                                   |
| - algorithm_name (e.g. "Random Forest Classifier")                                |
| - feature_set_version (e.g. "feat_v1.0")                                          |
| - training_dataset_version (e.g. "ds_v1.0_train")                                 |
| - training_timestamp (ISO DateTime)                                               |
| - hyperparameters (JSON string)                                                   |
| - metrics_serialized (JSON string of precision, recall, F1, ROC-AUC)              |
+-----------------------------------------------------------------------------------+
                                         |
                                         | (1:N)
                                         v
+-----------------------------------------------------------------------------------+
|                              recommendations                                      |
+-----------------------------------------------------------------------------------+
| - id (PK)                                                                         |
| - model_governance_id (FK -> model_governance.id)                                 |
| - part_id (FK)                                                                    |
| - expected_demand / quantile forecasts                                            |
| ...                                                                               |
+-----------------------------------------------------------------------------------+
```

## 2. Versioning Schema

### A. Model Version
Semantic versioning `MAJOR.MINOR.PATCH` is applied:
* `MAJOR`: Architectural model shifts (e.g., switching from Random Forest to XGBoost).
* `MINOR`: Schema or feature structure additions (e.g., adding a new operating intensity metric).
* `PATCH`: Model re-training runs on new chronological data snapshots without schema modifications.

### B. Training Dataset Version
Tracks the database snapshot and split bounds:
* Format: `DS_START_DATE_END_DATE` (e.g., `DS_20250101_20250831` representing data from Jan 1, 2025, to Aug 31, 2025).

### C. Feature Definition Version
Tracks the mathematical logic used to construct predictors (e.g., wear accumulation equations):
* Format: `FEAT_vX.Y` (e.g., `FEAT_v1.0` - simple operating hours and overdue statuses).

## 3. Metadata Schema Table (Database Addition)

To persist governance data, the schema includes the `model_governance` table:

```sql
CREATE TABLE model_governance (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    model_version TEXT NOT NULL,
    algorithm_name TEXT NOT NULL,
    feature_set_version TEXT NOT NULL,
    training_dataset_version TEXT NOT NULL,
    training_timestamp TEXT NOT NULL,
    hyperparameters TEXT NOT NULL,          -- JSON serialized dict
    metrics_serialized TEXT NOT NULL,       -- JSON serialized performance metrics
    is_active BOOLEAN NOT NULL DEFAULT 1
);
```

### Recommendation Linkage
The `recommendations` table is updated to reference this metadata:
```sql
ALTER TABLE recommendations ADD COLUMN model_governance_id INTEGER REFERENCES model_governance(id);
```

## 4. Traceability & Diagnostics

When an evaluator or dispatcher inspects a parts order recommendation:
1. The UI displays the generating model version (e.g. `v1.2.0-RandomForest`).
2. Clicking the version badge exposes:
   * Training date: `2026-08-28 14:50:00`
   * Hyperparameters: `{"n_estimators": 100, "max_depth": 8, "random_state": 42}`
   * Out-of-sample validation scores: `F1: 0.82, Precision: 0.79, Recall: 0.85, ROC-AUC: 0.89`
   * Data split coverage: Days 1 to 360.
3. This mechanism prevents "black box" recommendations and enables rigorous tracking of performance degradation over time.
